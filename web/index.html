Sin conexión verificada — esperando la API de continuidad

El panel lee la sesión de /api/continuity. Si la API no responde, no se muestra ningún resultado.

Tarea supervisada — qué pasó y en qué orden

Una tarea de programación real, ejecutada por el worker del servidor bajo política determinista. El guardia sólo escribe un mensaje: no ejecuta herramientas, no concede permisos y su mensaje no resuelve la tarea.

El servidor elige la tarea, la política y los límites; el panel no propone ruta, herramienta ni modelo. El botón queda deshabilitado mientras la sesión está en cola o en ejecución, para no lanzar una segunda tarea.

Si el core protege la escritura, sólo se envía en la cabecera X-Continuity-Key de las peticiones de esta pestaña, al mismo origen. No se guarda en el navegador, no se registra y no se muestra. Se descarta al cerrar el campo.

Qué pasó, en una frase

Ciclo de rescate — siete estados

Cada estado se pinta sólo si su campo viene informado. El orden de la secuencia es: DETECTED → INTERVENTION_SENT → INTERVENTION_RECEIVED → RESUMED. El desenlace es uno de tres: RESOLVED, UNRESOLVED o NO_INTERVENTION_NEEDED.

  • Cumplido: el servidor informa el campo como true
  • No cumplido: el servidor informa el campo como false
  • SIN DATO: el campo no viene; el panel no lo deduce de otro campo

Eventos tal como los entrega el servidor, en orden de llegada y sin duplicados. El panel no genera, resume ni completa el texto: si la API deja de responder, el registro se queda como está y el error se muestra arriba.

Sin eventos: todavía no hay ninguna sesión de la que leer evidencia.

    Alcance controlado. Una sola tarea, fija y elegida por el servidor: el panel no elige ruta, herramienta, modelo ni credenciales, y no puede pedir otro alcance.

    Sin flujo de aprobación humana. No hay ningún control en esta página que apruebe, conceda o amplíe permisos. Una operación denegada por la política sigue denegada, y el guardia no puede revertirlo.

    Un mensaje del guardia no es un resultado. Que el guardia escriba, o que el worker reciba el mensaje, no resuelve la tarea. Sólo se dice «resuelta» cuando el servidor informa intervention.resolved = true y verification.passed = true a la vez.

    «Completada» no es «resuelta». El estado completed de la sesión no se convierte en RESOLVED: es otro campo y el panel no lo sustituye.

    Campos opcionales. detected, withheld, guardCalls y guardTokens todavía no forman parte del contrato publicado. Si no llegan, el panel escribe SIN DATO: no inventa el estado. La tabla completa está en docs/sprint/panel-contract.md.

    El worker y el guardia usan Vultr Serverless Inference cuando el backend confirma modo live. El lugar de despliegue y el aislamiento requieren evidencia independiente: este panel no los certifica. Todo lo que muestra procede de /api/continuity; no se consulta ninguna otra ruta. Un campo ausente se muestra como «sin dato»; no se inventan eventos ni resultados.

    El operador puede iniciar una tarea fija. El guardia no concede permisos; la política y el sandbox siguen siendo la autoridad.

    POST /api/continuity/tasks · GET /api/continuity/tasks/:id · GET /api/continuity/status

    Ninguna de esas rutas se simula: un 404, un error de red o un cuerpo inesperado se muestran tal cual y el panel permanece vacío. El botón solicita una sesión al servidor; no concede permisos ni ejecuta pruebas en el navegador, y no guarda credenciales.
